Como o portal SPX Reversa é construído e onde a informação vive

Do navegador do operador até a linha no banco de dados: a tecnologia, as camadas de código, o modelo de dados e — o mais importante — como cada informação se conecta e “conversa” com as outras.

🌐 jornada-reversa.vercel.app ⚛️ React + Vite + TypeScript 🗄️ Supabase / Postgres 🔒 RLS no banco
01 — VISÃO GERAL

O que é o sistema

O SPX Reversa é o portal corporativo da Logística Reversa da Shopee: um “jornal + central de conhecimento” interno onde a equipe consulta procedimentos (POPs), notícias, dashboards, ferramentas, vagas, o time, projetos e um quiz semanal. Tudo é protegido por login e por aprovação — quem não tem acesso não enxerga nada do conteúdo.

Ele tem duas faces na mesma aplicação: o portal público interno (o que o operador vê) e um painel administrativo (onde o admin cria, edita e publica todo o conteúdo, controla acessos, abas e o quiz).

Camada 1 · Cliente

Navegador

Aplicação React que roda inteira no navegador (SPA). Renderiza as telas e conversa com o backend por HTTPS.

Camada 2 · Entrega

Vercel (CDN)

Hospeda e distribui os arquivos estáticos na borda. É de onde o site “baixa”. Publica automático a cada push na main.

Camada 3 · Dados

Supabase

Banco Postgres + Autenticação + Storage de imagens. É o cérebro: guarda tudo e decide quem vê o quê.

02 — ARQUITETURA

O caminho da informação, ponta a ponta

Uma requisição nasce no navegador, passa pela CDN da Vercel (só para carregar o app) e vai direto ao Supabase para ler/gravar dados. O banco aplica as regras de segurança (RLS) antes de devolver qualquer linha.

Ponto importante

Não existe um “servidor de backend” próprio para manter. O React fala direto com o Supabase; toda a lógica de segurança e permissão mora no banco (RLS + funções). Isso simplifica a operação e reduz superfície de ataque.

04 — CAMADAS DE CÓDIGO

Como uma informação viaja pelo código

Toda tela segue o mesmo caminho. Exemplo real: abrir a lista de POPs.

  1. Tela — src/pages/Pop.tsx precisa da lista e chama o hook useAsync(getPops).
  2. Camada de dados — src/data/content.ts → getPops() faz supabase.from('pops').select() e converte a linha do banco (snake_case) para o formato do app (camelCase).
  3. Cliente Supabase — src/lib/supabase.ts (uma única conexão) envia a requisição HTTPS com o token da sessão do usuário.
  4. Banco + RLS — o Postgres recebe, aplica as regras (o usuário está aprovado? é admin?) e devolve só as linhas permitidas.
  5. De volta à tela — os dados voltam, o React renderiza os cards. Escrita (admin) segue o mesmo caminho por src/data/admin.ts.
Leitura pública

src/data/content.ts

getNews, getPops, getJobs, getPeople… — buscam o conteúdo que o portal exibe.

Escrita admin

src/data/admin.ts

CRUD genérico dirigido por COLLECTIONS: cria/edita/apaga qualquer coleção.

Acessos & quiz

access.ts · quiz.ts

Aprovação de usuários, operações/localidades e o fluxo do quiz (com correção no servidor).

Configuração

settings.ts · navSettings.ts

Links globais (SPX Reverser, Vagas) e visibilidade/ordem/nome das abas.

06 — RELACIONAMENTO

Como as informações conversam entre si

As tabelas não são ilhas. O perfil do usuário é o eixo central: ele liga a identidade (login) às permissões, e à operação/localidade. E o RLS usa esse perfil para decidir, em cada tabela, o que a pessoa vê.

Fig. 2 — O perfil liga login → permissões → operação. O RLS lê esse perfil e é ele quem faz as tabelas “conversarem” com a pessoa certa.

As conexões, em palavras

  • Login → Perfil: ao cadastrar, um trigger cria automaticamente uma linha em profiles com o mesmo id do usuário do Auth. Perfil e login são a mesma pessoa.
  • Perfil → Permissão: se o e-mail está em admin_emails, o perfil vira admin; senão é viewer e precisa ser aprovado para ver conteúdo.
  • Operação → Localidade: cada localidade pertence a uma operação; no cadastro a pessoa escolhe as duas, e isso fica no perfil (usado nos relatórios do quiz por operação).
  • Quiz encadeado: quizzes tem várias quiz_questions; cada quiz_attempt (de um usuário) gera várias quiz_answers. A correção acontece no banco, nunca no navegador.
  • Config → Interface: nav_settings decide abas/ordem/nome; app_settings guarda links globais; reversa_now alimenta o painel da home. Mexer nessas tabelas muda o portal na hora.
  • O RLS é o tradutor: toda leitura passa por is_approved()/is_admin(), que consultam o profiles. É assim que “a informação certa chega na pessoa certa”.
  • Perfil → Segurança: tentativas de login erradas contam no profiles; ao travar, gera um registro em security_events que o admin vê e resolve ao liberar a conta.
  • Perfil → 2FA: o employee_code do SeaTalk fica no profiles; o login com 2FA cria um login_approvals e só abre o portal após a aprovação no bot.
07 — SEGURANÇA

O que protege os dados

No banco

Row-Level Security (RLS)

Ligado nas 23 tabelas. Sem uma regra que permita, a linha não sai do banco — nem por API direta.

Funções

is_approved() · is_admin()

Decidem leitura (aprovados) e escrita (só admin). O quiz é corrigido no servidor (submit_quiz).

Imagens

Storage restrito

Buckets avatars e media aceitam só imagem, até 6 MB.

Rede

Cabeçalhos HTTP

CSP, HSTS, X-Frame-Options e nosniff na Vercel — anti-clickjacking e anti-injeção.

Trava de acesso por tentativas (anti-invasão)

Depois de 5 tentativas de senha incorreta, a conta é bloqueada e só um administrador consegue liberar. A trava é ancorada no banco, não só na tela.

  1. Conta a falha — cada erro chama record_login_failure(), que soma a tentativa no perfil.
  2. Bloqueia no limite — ao chegar em 5, marca locked = true. Administradores nunca são travados (para nunca prender todos os admins).
  3. Fecha no banco — is_approved() passa a exigir conta não bloqueada: uma conta travada não lê nada, mesmo por API direta com a senha certa.
  4. Alerta o admin — o bloqueio registra um evento em security_events, que aparece como alerta de segurança no painel de Acessos.
  5. Só o admin libera — admin_unlock_user() desbloqueia e resolve o alerta. O usuário só volta a ver o portal depois disso.
Camadas de defesa contra força-bruta

O rate-limit nativo do Supabase Auth barra a força-bruta crua no endpoint de login; a trava de conta acima é a regra de negócio “bloqueia e só o admin libera”. O envio de e-mail ao admin no bloqueio já está previsto (gancho pronto) — falta apenas plugar um serviço de envio.

Verificação em duas etapas (2FA) por aprovação no SeaTalk

Opcional por usuário. Quando ligado, além da senha o login exige uma aprovação no bot do SeaTalk — em até 2 minutos, senão o acesso não é liberado.

  1. Senha OK, mas ainda barrado — com 2FA ligado, is_approved() exige uma aprovação recente; sem ela, o portal mostra “Aguardando aprovação no SeaTalk”.
  2. Solicitação no bot — a Edge Function seatalk-2fa pede um token do app SeaTalk e envia ao usuário uma mensagem com o link de aprovação (registro em login_approvals, validade 2 min).
  3. Aprovação — o usuário toca no link (página /aprovar no portal) e confirma. Isso libera o acesso por 12h.
  4. Identidade no SeaTalk — o employee_code de cada pessoa é capturado automaticamente: ao mandar “oi” ao bot, o Event Callback casa o e-mail com o perfil e salva o código.
Segredos do 2FA nunca vão ao navegador

App ID/Secret do SeaTalk ficam na tabela integrations (RLS: só a Edge Function lê). O navegador nunca fala direto com o SeaTalk — toda a conversa passa pela função no servidor.

Sobre a chave que aparece no código

A publishable key do Supabase é pública por design — ela só permite tentar acessar; quem realmente libera os dados é o RLS. A chave secreta (service_role) nunca vai para o navegador. Nenhum segredo fica versionado no Git.

2FA por e-mail — sem “oi” no bot

A verificação em duas etapas foi endurecida: a Edge Function descobre o employee_code de cada pessoa pelo e-mail corporativo (API get_employee_code_with_email, “No Limit”), sem depender de a pessoa iniciar conversa com o bot. Basta o funcionário estar no Service Scope (por departamento/subteam ou whitelist) para receber a aprovação com os botões Aprovar / Não fui eu.

Consideração de disponibilidade (não é falha)

Como record_login_failure precisa ser chamável antes do login, em tese alguém poderia forçar o bloqueio de uma conta conhecida (o admin destrava em 1 clique). É inerente a qualquer sistema de lockout; pode ser endurecido com captcha, se desejado.

08 — PUBLICAÇÃO

Como uma mudança chega ao ar

  1. Código — a alteração é feita e validada com npm run build.
  2. Commit + push — vai para a branch de trabalho no GitHub.
  3. Merge na main — a main é a branch de produção.
  4. Deploy automático — a Vercel detecta o push, faz o build e publica em jornada-reversa.vercel.app em ~1 min.
O banco é separado do deploy

Publicar o site não altera o banco. Conteúdo (notícias, POPs, quiz…) é gerenciado pelo painel admin em tempo real; mudanças de estrutura do banco são feitas à parte, direto no Supabase.

Code-splitting por rota (carregamento sob demanda)

Cada página virou um pacote separado (React.lazy + Suspense): o pacote inicial caiu de ~659 KB para ~446 KB (gzip 171 → 128 KB). Um operador que só lê POP não baixa mais o painel admin — melhora o LCP no celular/3G do CD.

Referência de leitura: FCP/LCP até ~2,5s = ótimo e até ~4s = bom · TBT até 200ms = bom · CLS até 0,1 = bom.
